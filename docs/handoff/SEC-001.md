# SEC-001 — Authentication hardening

## Summary

Jarvis no longer serves traffic when `JARVIS_PASSCODE` is unset. The only exception is `JARVIS_DEV_INSECURE=1` while the process is bound to loopback, and that path logs a banner that authentication is disabled.

The default bind is `127.0.0.1` (`python -m app` uses `JARVIS_HOST` / `JARVIS_PORT`). Listening on any other address, including `uvicorn --host 0.0.0.0`, requires `JARVIS_ALLOW_PUBLIC_BIND=1`.

The passcode is hashed with SHA-256 and compared with `hmac.compare_digest`. `POST /api/v1/auth/login` exchanges it for an opaque bearer token that expires (default 12 hours, `JARVIS_SESSION_TTL_SECONDS`). `POST /api/v1/auth/logout` revokes that token. Failed guesses on the login body and on `X-Jarvis-Passcode` share one lockout (default 5 failures, then 30 seconds, doubling up to 15 minutes). A session that was already issued keeps working during the lockout. A correct passcode does not skip the window.

Every HTTP route except `/health`, the PWA shell, and `POST /api/v1/auth/login` requires a credential. `/ws/logs` requires a token or passcode query parameter. `/ws/node` still requires an enrolment token or the node secret.

Recorded as D-026. Implementation commit `5909475` on `jarvis/sec-001`.

## Assumptions

- The passcode header remains a valid credential next to the bearer token, so the MCP server, node-enrol curls, and existing tests keep working. It uses the same lockout. Logout ends the session token and leaves the passcode in place.
- Sessions and the lockout live in the process. A crash drops both. Sessions fail closed (log in again). Resetting the lockout requires a process restart, which a remote client cannot do.
- One worker. `python -m app` does not start a pool. Extra uvicorn workers would each keep their own sessions and counter.
- The PWA shell (`/`, `/static/*`, favicon, manifest, service worker) is public so the lock screen can load. `/health` stays public for probes. `/docs`, `/redoc`, and `/openapi.json` require auth. `OPTIONS` is not gated, so a cross-origin preflight can finish; the real request is still checked.
- A blank `X-Jarvis-Passcode` counts as “no credential”, not as a guess. An empty login body counts as a failure.
- Lockout is global, not per IP. This is a single-user system; a per-address bucket would let someone rotate around it.
- The log WebSocket takes `?token=` or `?passcode=` because a browser cannot set handshake headers. HTTP headers on that upgrade are ignored, so a bad query cannot be rescued by a header the client library attached.
- `/ws/node` keeps authenticating the first `hello` with an enrolment token or the node secret. It does not use the user session. The HTTP fleet routes do.
- Invalid numeric settings fall back to the defaults (12h TTL, 5 failures, 30s backoff) so a typo cannot turn expiry off.
- Tailscale Funnel proxies to localhost, so the host unit now runs `python -m app` on `127.0.0.1` instead of `--host 0.0.0.0`.
- The branch is `jarvis/sec-001` (lowercase). The ticket id is SEC-001.

## Known gaps

- Sessions do not survive a restart. That is fail-closed, and it does mean a phone has to unlock again after a reboot.
- The lockout counter resets on restart.
- A WebSocket token in the query string can show up in an access log. It expires and logout revokes it. The passcode is no longer put in that query by the PWA.
- The token is a random secret stored as a SHA-256 hash, not a signed JWT. Passkeys are still the later phase in D-004.
- A bind that never appears as `JARVIS_HOST` or uvicorn `--host` (for example a socket handed in by a supervisor) is not inspected.
- Several uvicorn workers would not share the lockout.

## Security impact

- An unset passcode cannot leave the API open. The loopback dev switch is explicit and noisy.
- The process no longer listens on every interface unless that is opted into.
- Online guessing of the passcode locks the login door, including guesses sent as the header.
- A stolen session token stops working at expiry or at logout.
- Unauthenticated calls to the API, the log stream, and the node socket are rejected. `/health` still answers without a credential and does not return secrets.

## Rollback

1. Check out `main` (or revert commit `5909475` and this handoff commit). No database migration was added, so there is nothing to undo in Postgres or SQLite.
2. If the host unit was changed to `python -m app`, put the previous `ExecStart` back and `systemctl daemon-reload`. The previous unit listened on `0.0.0.0`.
3. Clients that already stored `jarvis.token` will be logged out by a rollback and will need the passcode again. Clients that still send `X-Jarvis-Passcode` work on both sides.
