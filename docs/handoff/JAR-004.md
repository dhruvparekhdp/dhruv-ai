# JAR-004 — Deny-by-default permissions at the tool boundary

## Summary

Tool execution for agents goes through one function, `app.tools.executor.execute_tool`. A name that is not in the registry is denied. Every tool declares a policy level: `read`, `internal_write`, `external`, or `dangerous`. `external` and `dangerous` do not run until a stored approval matches a SHA-256 of the tool name and the canonical parameters. The executor recomputes that hash. The approval expires after 15 minutes (`JARVIS_APPROVAL_TTL_SECONDS`) and is single-use. The row records who decided, when, the decision, the params hash, and the mission id, in the mission database.

`MissionScheduler` is still the only dispatcher. The runner does not call a handler itself, and an agent id is not a tool, so agents cannot call each other.

Branch `jarvis/jar-004` was created from `main` (`8ba215e`). The ticket asked for `jarvis/JAR-004`; this environment only keeps lowercase branch names. A new branch was allowed. SEC-001 and SEC-002 are on their own branches and are not in this one.

## Assumptions

- The older `SAFE` / `SENSITIVE` / `DANGEROUS` label stays. Tests and `drills/cases/drill_08.py` name it, and `GET /api/v1/tools` still returns it. The policy level is a second field. `web.fetch` and `web.search` stay `SAFE` on the old label and are `external` on the new one, so they now park.
- `fs.write` is `internal_write`. It changes a file on the operator's own node and can be written again. `shell.exec` and `fs.delete` stay `dangerous`.
- Canonical params drop keys that start with `_`. The executor injects `_mission_id` and `_agent_id` after the hash check. Object keys are sorted. List order is part of the action.
- A mismatched call does not consume the approval. A second use of a matched call does.
- "Approvals survive restart" is a fresh database connection, the same check the mission store already uses for missions. There is no in-memory approval cache.
- `POST /api/v1/nodes/dispatch` is the signed-in operator, not an agent. It still calls the node gateway directly. Agent calls do not. The matrix says so.
- Default lifetime is 15 minutes from creation, stored on the row, so changing the setting later does not extend an approval that already exists.

## Known gaps

- The rate of the approval window is per process only in the sense that the row is in the database: two processes sharing Postgres would see the same row. The consume update is conditional on `consumed_at IS NULL`, so one of two racers wins.
- The operator dispatch endpoint is a second path onto node tools. Closing that would make the Files and System panels park for an approval of the human's own click.
- This environment could not run the Postgres job. Run `JARVIS_TEST_DATABASE_URL=postgresql://... pytest -q` before relying on the column migration there.

## Security impact

An unregistered tool cannot run. A web fetch or a web search no longer leaves the machine on the model's request alone. `memory.forget`, `fs.delete`, and `shell.exec` still park, and an approval of one argument set cannot be replayed against another, reused, or used after it expires. The decision is in the database with the identity of the decider.

## Rollback

Do not merge the pull request, or revert the commits on `jarvis/jar-004`. No package change. Existing approval rows gain three columns on the next `init_db`; leaving those columns in place is harmless if the code is reverted. New approvals created by this revision store a hash the old code ignores.
