# TRD-007 — Alerts and the daily trading briefing

## Summary

Four rules write to an in-app inbox: an active signal with strength above X, an engine whose `data_as_of` is older than N minutes, a paper or shadow book whose peak-to-trough drawdown is above Y percent, and each named risk-limit breach. Equal to the threshold does not fire. Quiet hours are the Asia/Kolkata wall clock, `[start, end)`, wrapping midnight. A row held for quiet hours is stored as suppressed and is not listed, and it does not start the dedupe window. A delivered key is not delivered again until the window has passed.

The daily briefing is a mission with five sections — market, signals, positions, performance, alerts — each with its own as-of. The text is filled in Python and the tasks are stored already SUCCESS, so the planner never rewrites them. Performance figures come from the outcome arithmetic. A symbol that was not in the positions input is not named. An unavailable read says unavailable and `as_of unknown`.

`GET /api/v1/alerts` is passcode-gated and returns delivered rows. The PWA lists those rows. Nothing in `app/alerts/` sends mail or opens an HTTP client.

## Assumptions

- Branch is `jarvis/trd-007`, cut from `jarvis/trd-006` (`5a58187`), not from `main`. `main` does not contain the trading contract, the adapters, or the outcome math this ticket reads. The pull request targets `jarvis/trd-006` so the diff is only TRD-007. TRD-006 was already committed and pushed. This environment allowed the new branch.
- Strength, drawdown percent, and feed age use a strict greater-than. 0.70 does not clear a 0.70 bar. Age of exactly N minutes is not stale. A missing `data_as_of` is not stale.
- Y in "drawdown > Y%" is a percent (`5` means 5%). The ratio is `(peak - equity) / peak` along the currency-drawdown walk. The hand book peak is 15 and the drop is 9, so the percent is 9/15. A book that never trades above zero has no percent and the rule does not fire.
- Quiet hours default to 22:00–07:00 IST. 22:00 is inside. 07:00 is outside. The machine timezone is not used.
- Dedupe default is 60 minutes. A delivery at 08:00 IST is still a duplicate at 09:00 and is a new delivery at 09:01. Only a delivered row holds the window.
- Default severity is warning for a signal and a stale feed, critical for drawdown and a risk breach.
- The briefing time defaults to 08:00 IST. It is due at that time if that IST date has not already run. There is no background thread. A caller passes `now`.
- Positions text is the symbol list and nothing else. Performance text is sample size and period from `compute_outcomes`. Trades that were passed in but marked unavailable are not scored.
- The commit trailer `Co-authored-by` is inserted by the environment. It was left in place because rewriting history is not allowed. The message itself was written without that line.

## Known gaps

- Nothing calls `briefing_due` on a clock. The host has to invoke it. With the engine base URL unset, a briefing built from empty inputs says unavailable and does not invent a price.
- Each quiet-hours evaluation of the same key writes another suppressed row. Those rows stay out of the inbox and do not extend the dedupe window.
- The PWA lists delivered alerts. It does not render the briefing as its own screen; the briefing is a completed mission.
- Drawdown uses one page of trades the caller already has. This ticket does not fetch `/trades`.

## Security impact

- Delivery is the inbox table and `GET /api/v1/alerts`. The route uses the same passcode gate as the other `/api/v1` routes. There is no mail, webhook, Slack, or push path. `app/alerts/` does not import an HTTP or SMTP client.
- The rules do not place, cancel, or size an order, and they do not mount `/integration/v1`. A risk breach is a name from a read, not an instruction to flatten.
- Thresholds come from `ALERT_SIGNAL_STRENGTH_MIN`, `ALERT_STALE_MINUTES`, `ALERT_DRAWDOWN_PERCENT`, `ALERT_DEDUPE_MINUTES`, `ALERT_QUIET_HOURS`, and `BRIEFING_TIME`. Those are not secrets. A bad value keeps the default.

## Rollback

Revert `jarvis/trd-007`. The inbox table is created with `CREATE TABLE IF NOT EXISTS`, so an old process that never calls `alert_store.init_db` simply does not read it. Dropping `alerts` removes the inbox. Briefing missions already stored remain ordinary completed missions.
