# JAR-006 — Memory provenance

## Summary

Every memory row now carries `source` (`user`, `agent`, `tool`, or `import`), `source_ref` (a mission or message id, or empty), `created_at`, `confidence` (0 to 1), `sensitivity` (`normal` or `private`), and `expires_at` (nullable).

A correction inserts a new row and sets the previous row's `superseded_by` to the new id. The new row's `supersedes` points back. `read`, `list_all`, search, and `stats` return only the current row that has not expired. `get` by id still returns a previous version so the link can be inspected.

`DELETE /api/v1/memory/{id}` hard-deletes that fact and every version linked to it, and writes one `memory_audit` row per deleted id. The audit row stores the key and the action, not the value. `POST /api/v1/memory/retention` is the retention job; the same purge also runs once at boot. An expired current version takes its replaced versions with it.

Secrets are refused, not stored in redacted form. `app/memory/secrets.py` detects bearer tokens, labeled passwords, keys, and one-time codes, and a key whose name is itself a credential. The error names the kind of credential and does not echo the secret.

## Assumptions

- `confidence` is a float from 0 to 1. The default is 1. The HTTP API is the user, so `POST /api/v1/memory` always stores `source=user`. Agents writing through `memory.write` store `source=agent` and the mission id in `source_ref`. `tool` and `import` are accepted and have no caller yet.
- The previous free-form source `agent:{id}` is no longer stored. The agent id is not `source_ref`; that field is a mission or message id.
- Retrieval hides superseded and expired rows. A direct `get` by id still returns them until a hard delete or a purge removes them.
- Deleting any id in a chain deletes the whole chain, so a client that still holds the id from before a correction still forgets the fact. That keeps the existing API test's delete-after-edit behavior.
- The audit table does not copy the value. Hard delete would not be hard if the fact survived in the audit log.
- A sentence that only mentions the word "password" is still stored. A labeled secret (`password=...`, `Authorization: Bearer ...`, `totp=654321`) or a key named `password` / `api_key` / `token` is refused.
- An expired fact is hidden from retrieval immediately. The row remains until the retention job runs. Boot runs it once. `POST /api/v1/memory/retention` runs it again.
- Optional integrations and `/health` are unchanged.

## Known gaps

- Postgres was not run.
- The add-a-fact form does not collect sensitivity, confidence, or expiry. The API does, and the panel shows them when they are set.
- Superseded rows that have no `expires_at` stay in the database until the current version is deleted, the current version expires (the chain is purged with it), or someone deletes the fact. They are not returned by retrieval.
- `source=tool` and `source=import` are valid and unused.
- The unique index is dropped and recreated on every boot (`idx_memory_unique` replaced by `idx_memory_current`). That is intentional so databases created before this ticket can store a correction.

## Security impact

Secrets that match the detector are not written to `memory_entries` or `memory_audit`. The refusal message does not include the secret. Audit rows for a real delete record the key and the action only.

`private` is a label for the panel. It does not encrypt the row or hide it from the owner, who is the only user of this process.

The retention route is behind the same passcode as the rest of the API. The purge on boot does not need a request.

## Rollback

Revert the JAR-006 commits on `jarvis/jar-006`. New columns are nullable or defaulted, so old inserts still run if the code is rolled back and the columns are left in place. The partial unique index must be dropped and `idx_memory_unique` recreated if two rows already share a key, otherwise a later in-place update of that key fails. `memory_audit` can be dropped; nothing else reads it.
