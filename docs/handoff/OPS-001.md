# OPS-001 — Correlation IDs, structured logs, health

## Summary

HTTP requests now carry an `X-Correlation-ID`. A missing or unsafe value is replaced with a generated `cid_` id; a safe caller-supplied id is kept and echoed on the response. That id is stored on the mission, on each task, and on each audit row (`agent_messages`), and the scheduler re-binds it when the background run starts so the id survives the request.

`jarvis` logs are one JSON object per line: `level`, `timestamp`, `correlation_id`, `mission_id`, `component`, `message`. A filter redacts bearer tokens and labeled passwords, keys, tokens, and TOTP-style values before the line is formatted. Tests use fake secrets only.

`GET /health` is unchanged as the liveness document the PWA already reads. `GET /ready` is unauthenticated and reports the database, the scheduler, and whether groq, gemini, search, telegram, and the echo engine are configured. An unconfigured optional integration does not fail readiness. A failed database ping returns 503.

The done check is `tests/test_observability.py::test_one_request_id_traces_a_full_mission`: one id is asserted on the response, the mission, its tasks, its audit rows, and the `jarvis.scheduler`, `jarvis.runner`, and `jarvis.engines` log lines for that run.

## Assumptions

- `/health` stays the document `app/static/app.js` and `test_health_is_open_and_reports_real_state` already require (`storage`, `engines`, `telemetry`). It still calls `telemetry.stats()`. Liveness-versus-readiness is split by adding `/ready`, not by stripping `/health`.
- Optional integrations (groq, gemini, search, telegram) are reported as `configured` or `unconfigured`. Only a failed database ping or a missing scheduler fails `/ready`. The product is designed to boot on the echo engine with no keys.
- Adapter calls are the `jarvis.engines` log line (`adapter call provider=… model=…`). They are not a new telemetry column. The runner logs `agent step` and the scheduler logs dispatch. Goals and prompts are not written on those lines.
- The correlation id is persisted so a resumed mission logs under the id stored with it, not under whatever request happens to be in flight.
- An id is accepted only when it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. Anything else is replaced, so a caller cannot inject a newline or a space into the log or the response header.
- The middleware is raw ASGI. `BaseHTTPMiddleware` runs the endpoint in a child task and would drop the context var.

## Known gaps

- Redaction is pattern-based. An unlabeled secret, or one split across lines, is not removed. A labeled value is replaced with `[REDACTED]`.
- `/ready` treats the scheduler as ready when the process singleton exists. It does not prove a node is connected.
- WebSocket connections are not assigned a correlation id. Mission creation is HTTP.
- Existing databases gain `correlation_id` via `ALTER TABLE` on boot. Rows written before that column existed read back as an empty id.
- SQLite only was run. Postgres should be run before this is treated as storage-complete: `JARVIS_TEST_DATABASE_URL=postgresql://... pytest -q`.

## Security impact

`/health` and `/ready` stay unauthenticated, matching the existing probe. `/ready` says which integrations have a key configured. It does not return key material, a database URL, or an exception string. `ping_database` swallows the driver error for that reason: a Postgres failure can include the connection URL.

The response header echoes only a validated id. Audit payloads in the database still contain the mission goal, as they did before; the new log lines do not.

## Rollback

Revert `5f5b201` (`Carry a correlation id through missions and JSON logs.`) and the handoff commit that follows it. The new column is nullable with a default, so leaving it in place after a code rollback does not break the old inserts. Dropping it is optional and is not required to restore the previous behavior.
