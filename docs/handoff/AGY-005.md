# AGY-005 — Content workflow

## Summary

A content item now moves through a fixed server-side graph:

`idea → research → brief → outline → draft → creative_brief → review → approved → scheduled → published → analyzed`

plus `archived`. The only legal moves are the next step in that chain, a move
to `archived` from any live state, and `archived → idea`. A direct edit cannot
set `status`. New items and duplicates start at `idea`.

Entering `approved` requires an `agy_approvals` row whose latest decision for
that item is `approved` and whose `approver_id` is an `agy_approvers` row for
the same brand. A pending decision, a newer rejection, a decision with no
approver, or an approver from another brand does not open the gate. The
refusal uses one message so another brand's approver names are not returned.
Profile `approval_contacts` from onboarding are still names on the sheet.
They are not this allow-list.

Every create, title or body edit, duplicate, and successful transition writes
an `agy_content_revisions` row: author, timestamp, title, and body. Two rows
are diffable by comparing those snapshots. A refused transition writes nothing.

`published` stores `published_url` (http or https) and `published_on` (a
calendar date). The handler does not fetch the URL and does not call a
platform. `scheduled` still only writes a local channel and time, and the
channel must belong to the item's brand. That brand check runs before the
graph, so a cross-brand channel is refused even when the step is not legal yet.

## Assumptions

- The branch is `jarvis/agy-005`, lowercase, created from `jarvis/agy-003`
  (`9d532d2`). `origin/main` (`8ba215e`) has no agency package, so a branch
  from main would not compile. This ticket uses `BrandScope` and the content
  tables from the earlier tickets. The pull request targets `jarvis/agy-003`
  so the diff is only this ticket. This environment did allow a new branch.
  The ticket name `jarvis/AGY-005` is the same branch in lowercase, because a
  case-insensitive checkout cannot hold both.
- There is no backward rework edge. A rejected review is archived, or it stays
  in `review` until a later approval. Returning from `archived` lands on `idea`.
- The latest decision wins. An older approval does not override a newer
  rejection. Decisions with a null `approver_id` (the older helper used by the
  duplicate test) do not open the gate.
- An approver is a name and an optional email for one brand. It is not a login.
- Author on a revision is the name sent with the write. It is not a user id.
- Revisions store the full title and body. The table does not store a unified
  diff. Create notes the row `created`, an edit notes `edit`, a duplicate notes
  `duplicated`, and a transition notes `status: <from> -> <to>` unless the
  caller sent a note.
- `in_review` rows from earlier builds become `review` on the way up. The way
  down maps any status outside the old set (`draft`, `in_review`, `approved`,
  `scheduled`, `archived`) to `draft`, then drops the new columns. That loses
  the workflow state, the published URL and date, revision author and title,
  and the approver link.
- SQLite 3.45.1 cannot `ALTER TABLE ... DROP CONSTRAINT`, and rebuilding
  `agy_content_items` while foreign keys are on fails inside the migration
  transaction. `0004` is the only script that carries `sqlite-fk:off`. The
  runner turns foreign keys off for that script, rebuilds, writes the version
  row, commits, and turns them back on. Postgres ignores the marker and swaps
  the check constraint by looking up the status check on `agy_content_items`.
- `published_on` is stored as text `YYYY-MM-DD`. The URL is not requested.
- Tests use the placeholder names Ada and Bea and `https://example.com/post`.
  No new runtime dependency. No LLM call.

## Known gaps

- There is no path from `review` back to `draft`. Rework is archive, then idea.
- `published` and `scheduled` do not talk to a channel. A later ticket would
  have to add a real send, and it would still need an explicit human step.
- Approver email is not verified. Deleting an approver who already decided is
  a conflict; the decisions stay.
- Revision history is the full list for one item. There is no page size on
  `GET /content/items/{id}/revisions`.
- The publish URL is checked for `http://` or `https://` and whitespace. It is
  not resolved, and a date string longer than ten characters is read from its
  first ten characters when those ten are a calendar date.

## Security impact

- New read/write surface for approvers, decisions, transitions, and revisions,
  behind `X-Jarvis-Passcode` when a passcode is configured.
- Brand scope still applies. A transition, revision list, or decision for an
  item in another brand returns 404 and does not change the row. An approver
  from another brand is "unknown" for this brand.
- Entering `approved` is refused without a current approval from an allowed
  approver of that brand. The error does not name the other brand's people.
- The published URL is stored and not fetched, so the mark is not a request
  to an attacker-controlled host.
- No broker, exchange, publishing, email, or ad-network calls. No secrets in
  code, tests, logs, or this document. Approver email is contact text, not a
  credential, and the tables have no password or token column.

## Rollback

Drop the workflow columns and the approver table, leaving earlier agency
migrations in place:

```bash
python -m agency.migrate down --steps 1
```

That removes `0004`. Statuses that `0004` introduced are folded to `draft`
first. `published_url`, `published_on`, revision `author` and `title`,
`agy_approvals.approver_id`, and `agy_approvers` go away. `agy_brand_profiles`
and `source_item_id` stay.

```bash
python -m agency.migrate down
```

drops every `agy_` table when nothing remains applied.

To remove the feature from the app, revert the AGY-005 commits. Boot still
calls `migrate_up()`. While this code is imported, the next start applies
`0004` again if it is missing.
