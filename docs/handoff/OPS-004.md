# OPS-004 — LLM usage tracking and budgets

## Summary

Every successful call through the engine router is one row in `llm_calls`: tokens in, tokens out, provider, model, and an estimated cost. The row is attributed to the mission and agent that made it. Chat turns are recorded too, under the agent id `chat`, with no mission.

Cost comes from a price table, USD per million tokens. Built-in rows cover the default Groq model, the default Gemini model, and the local echo model (explicitly free). `JARVIS_PRICE_TABLE` overlays that table. A model with no row is charged a fallback rate and marked `price_known: false`, so an unknown cloud model is not stored as free.

Three spend budgets sit on top of the ledger:

- mission — estimated spend of that mission (`JARVIS_BUDGET_MISSION_USD`, default 1)
- day — estimated spend of the UTC day (`JARVIS_BUDGET_DAY_USD`, default 5)
- agent — estimated spend of that agent during the UTC day (`JARVIS_BUDGET_AGENT_USD`, default 2)

Crossing one pauses the mission in `NEEDS_APPROVAL`, writes the reason onto the mission, and creates an approval named `budget.exceeded`. The mission is not marked `FAILED`, and the call that crossed the line stays in the ledger. No further model call is made for that mission. `GET /api/usage` returns daily, per-agent, and per-mission totals plus the recent calls.

The older task, time, and tool-call ceilings still abort a mission. Those are structural limits. The new ones are spend limits.

## Assumptions

- Spend budgets are estimated USD. The existing `Budget` fields (`max_tokens`, `max_tasks`, `max_seconds`, `max_tool_calls`) still abort. Changing those to a pause would have broken the mission tests that require a terminal failure.
- A budget trips only when spend is strictly greater than the limit. The echo model is priced at 0, so local chat does not pause a mission.
- The agent budget is per agent per UTC day, not for the lifetime of the agent. A lifetime cap would pause that agent permanently after one busy day.
- "Day" is UTC, matching the timestamps the rest of the process writes.
- Prices in code are estimates, not an invoice. Override them with `JARVIS_PRICE_TABLE`. Empty budget env vars use the defaults above; `0` is a real zero.
- Cost is stored as micro-USD (millionths of a dollar) so both databases share one integer. The API prints USD with six decimal places.
- Approving `budget.exceeded` records the decision and does not resume the mission. The pause is visible; continuing after approval is not built.
- `GET /api/usage` requires the passcode, like the rest of the API. Agent and mission breakdowns default to today. `daily` lists every day unless `mission_id` filters the ledger. `day=YYYY-MM-DD` selects another UTC day for the today window.

## Known gaps

- Postgres was not run.
- A paused mission stays paused until something else moves it. There is no resume path after the approval is granted.
- The fallback rate for an unknown model is 1 USD per million tokens, input and output. It is a stand-in so the cost is not zero, and `price_known` is false.
- Failed provider attempts are not rows. Only the call that returned a usable result is recorded.
- The PWA does not show the usage page.

## Security impact

The ledger stores token counts, provider, model, and cost. It does not store prompts or completions. The approval payload stores the budget reason, not the user text.

`GET /api/usage` is behind the passcode. The price table and budget numbers are configuration, not secrets. A bad `JARVIS_PRICE_TABLE` is ignored and the built-in table is used.

## Rollback

Revert the OPS-004 commits on `jarvis/ops-004`. Drop `llm_calls` if you want the rows gone; nothing else reads them. Unset `JARVIS_BUDGET_*` and `JARVIS_PRICE_TABLE` if they were added to a host env. The structural mission budgets are unchanged.
